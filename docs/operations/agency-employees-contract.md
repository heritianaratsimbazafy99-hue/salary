# Contrat SQL — salariés agence

Fondations : `20261023105030_agency_employee_lifecycle.sql`.

Toutes les mutations sont service_role exclusivement, avec `p_actor_id` réel issu de la session serveur. Agence revérifiée via profil actif, agency_memberships et agence active. Lectures session authenticated, rôle agency_manager (son agence) ou RH/superadmin (toutes agences actives). Aucun droit nouveau team_manager.

## RPC stabilisées

- `agency_employee_directory(p_agency_id uuid default null, p_search text default null, p_state text default null, p_employee_id uuid default null, p_limit integer default 25, p_offset integer default 0)` → JSONB array. Éléments : `id`, `agency_id`, `matricule`, `email`, `full_name`, `is_active`, `has_access` (compte rattaché, accès actif reste `is_active`), `revision`, `state`, `lifecycle_revision`, `started_on`, `departed_on`, `departure_reason`, `operational_revision`, `has_hr_record`, `job_title`, `department_id/name`, `site_id/name`, `team_id/name`, `manager_profile_id/name`, `contract_type/start/end`, `total_count`. L’état absent par défaut liste CURRENT et TO_REVIEW; DEPARTED pour archives. Détail via p_employee_id. operational_revision toujours entier, même sans données.
- `agency_employee_options(p_agency_id uuid)` → `{departments:[{id,name}],sites:[{id,name}],teams:[{id,name,site_id}],managers:[{id,full_name}]}`. Références actives seulement.
- `agency_employee_history(p_employee_id uuid)` → array `{id,action,actor_profile_id,actor_name,actor_role,created_at,employee_revision,lifecycle_revision,before_employee_revision,before_lifecycle_revision,operational_revision,before_operational_revision,changed_fields,result}`. Métadonnées minimales, sans valeurs privées. Le motif de correction est conservé dans la table audit restreinte; la projection manager ne le renvoie pas.
- `agency_employee_requests(p_employee_id uuid default null)` → array `{id,employee_id,agency_id,kind,requested_value,reason,status,revision,employee_revision,lifecycle_revision,created_by,created_at,decided_by,decided_at,decision_reason}`. Toutes les demandes actives PENDING et APPROVED_PENDING_VERIFICATION sont renvoyées, ainsi que les 500 dernières terminées, sans plafond global masquant une action ancienne. La projection inclut aussi employee_name, matricule, agency_name, created_by_name, current_value, requested_display_value, previous_value, departed_on et contract_type/start/end pour décision éclairée. Une requête EMAIL approuvée a status APPROVED_PENDING_VERIFICATION, jamais EXECUTED sans workflow Auth vérifié.
- `agency_create_employee(p_actor_id uuid,p_agency_id uuid,p_matricule text,p_email text,p_full_name text)` → UUID. Création minimale, pas d’invitation ni compte Auth. Pour un acteur agency_manager, un email déjà présent dans profiles exige un traitement RH (PT409 identity_requires_hr_review), sans rattachement automatique. Matricule canon partagé 1..80 points Unicode.
- `agency_save_employee(p_actor_id uuid,p_employee_id uuid,p_revision integer,p_operational_revision integer,p_full_name text,p_job_title text,p_department_id uuid,p_site_id uuid,p_team_id uuid,p_reason text)` → void. Valeurs nullable pour dossier partiel; poste/organisation complets sont synchronisés au dossier RH existant, aucun contrat modifié. Révision identité et opérationnelle obligatoires.
- `agency_depart_employee(p_actor_id uuid,p_employee_id uuid,p_revision integer,p_lifecycle_revision integer,p_departed_on date,p_reason text)` → void. Motif 1–300, date <= jour Madagascar, conflits RH bloquants PT409, accès inchangé.
- `agency_request_employee_change(p_actor_id uuid,p_employee_id uuid,p_revision integer,p_lifecycle_revision integer,p_kind text,p_requested_value text,p_reason text)` → UUID. kind RETURN/MATRICULE/EMAIL/MANAGER. RETURN valeur date ISO; MANAGER UUID ou chaîne vide pour retrait. Demande seulement, révisions gelées.
- `hr_decide_employee_change(p_actor_id uuid,p_request_id uuid,p_revision integer,p_approve boolean,p_reason text)` → void. RH seulement. RETURN/MATRICULE/MANAGER appliqués atomiquement si révisions identité/lifecycle encore valides; EMAIL → APPROVED_PENDING_VERIFICATION seulement (agent intégration implémente confirmation Auth séparée).

Erreurs: forbidden 42501, not_found P0002, stale_revision PT409, lifecycle_conflict PT409, invalid_input 22023, contraintes unicité 23505. Les mutations doivent être suivies d’un rechargement.

## Tables et helpers pour autres migrations

- `employees.revision integer not null default 1`, trigger toute UPDATE métier, pas d’incrément si identique. Ne pas faire dépendre une requête revue de updated_at seulement.
- `employee_employment_lifecycle(employee_id PK,agency_id,state text,started_on,departed_on,departure_reason,revision,updated_at)`; après INSERT employees: CURRENT automatiquement. Backfill existants: TO_REVIEW si is_active=false ou statut RH INACTIVE/CONTRACT_ENDED, sinon CURRENT. Aucune date fictive.
- `employee_agency_operations(employee_id PK,agency_id,job_title?,department_id?,site_id?,team_id?,revision,updated_at)` : complétion partielle. Dossier RH complet existant synchronisé par trigger; edits manager vont dans RH si complet. Source de lecture unique cette table pour poste/organisation; manager/contrat issus RH.
- `agency_employee_change_requests`, `agency_employee_events` (purge événements seule après 12 mois), `employee_employment_episodes` conserve transitions sans purge.
- `private.agency_require_actor(p_actor_id uuid,p_agency_id uuid)` → public.profiles; manager agence ou RH global; partage verrous profil/agence/membership.
- `private.agency_employee_event(p_actor_id uuid,p_employee_id uuid,p_action text,p_result text default 'SUCCESS')` → void, audit minimal atomique. Réutilisable import/paie/invitations.

Ordre des verrous : pour création/import, table profiles avant profil acteur ; puis acteur/agence → employees (lots UUID croissant) → lifecycle → opérations/RH → demande. Ne pas modifier lifecycle/is_active par import ou invitation. Aucun nom existant écrasé par paie/provisioning.

Vérification locale : reset complet et 19 suites SQL/shell réussies via orchestrateur, y compris les quatre courses contrôlées. Voir le compte rendu de vérification du 23 octobre 2026. Aucun résultat de production revendiqué. Les fonctions de planning refusent DEPARTED aux écritures actives; ENDED/CANCELLED restent possibles. Le retour sans dossier RH reste partiel; avec dossier RH, statut/dates de contrat doivent être compatibles. Les demandes MANAGER gèlent aussi la révision du dossier RH.

## Intégration paie et invitations (20261023105206)

- `review_payroll_import(import_id)` vérifie le lecteur réel, l’agence active et l’expiration; projection SECURITY DEFINER nécessaire car lifecycle reste privé. Empreinte : import + lignes complètes + UUID/révision identité/révision lifecycle/état. Destinataires : `departed`, `nameDiffers` en plus des champs existants.
- `approve_departed_payroll(p_actor_id,p_import_id,p_fingerprint)` service/RH seulement, audit transactionnel. L’approbation est attachée à l’empreinte exacte ; toute modification pertinente exige une nouvelle revue et validation. Écran `/hr/payroll-departure-review/[importId]`. Le responsable publie ensuite par le parcours habituel.
- La publication conserve le nom du dossier et le snapshot source. Un DEPARTED avec accès désactivé reste publiable après validation, sans modification de `is_active` ni de lifecycle ; l’envoi d’une invitation reste interdit. Remplaçants candidats DEPARTED exclus.
- `queue_agency_invitations(p_actor_id,p_agency_id,p_employee_ids,p_operation_id)` crée les jobs après création indépendante; droits/agence/état/email vérifiés serveur. Le même identifiant d’opération réutilise les jobs. Délai de renvoi : 60 secondes. Aucun compte/profil n’est créé par cet envoi.
- `claim_agency_invitation(p_job_id,p_token_hash)` recontrôle acteur et dossier avant chaque tentative, interdit départ/accès désactivé/compte existant/changement EMAIL en cours de vérification. Lease 5 minutes, 10 tentatives maximum. Aucun jeton brut en base : dérivation HMAC en mémoire depuis UUID job + secret serveur.
- `POST /api/manager/employees/invitations` corps strict `{employeeIds: UUID[], idempotencyKey: UUID}`. Réponse `{sent,failed,skipped,pending}`. Composant `AgencyInvitationButton({employeeIds})` pour individuel/sélection, à proximité des adresses affichées. Bienvenue sans mention d’une fiche déjà disponible.
- Les jobs restants/échecs sont repris par `/api/cron/agency-invitations` (CRON_SECRET), toutes les 15 minutes dans `vercel.json`. Lot maximal 20 envois et budget 240 secondes. Les reprises conservent jeton et clé Resend ; arrêt automatique après 23 heures suivant la première tentative afin de rester dans la fenêtre d’idempotence fournisseur de 24 heures. Après cette fenêtre, le responsable peut déclencher explicitement une nouvelle invitation après examen du résultat fournisseur. Les résultats externes inconnus ne sont jamais affichés comme des envois réussis.
- Une ancienne invitation ne permet aucune activation d’un DEPARTED, même si son accès historique est maintenu. Vérification email Auth indépendante toujours obligatoire ; compte multi-agence conservé sans duplication par activation liée au même Auth user vérifié.

Validation locale dédiée : `scripts/tests/agency-payroll-invitations.sql` (transaction avec rollback, inclut appel de revue sous authenticated et refus du lecteur hors périmètre). Complète les suites de régression `employee-identity.sql` et `payroll-manager-review.sql`.


## Garde livraison pendant correction d’email (20261023111856)

`payroll_email_delivery_allowed(p_agency_id,p_email)` est une RPC SECURITY DEFINER réservée au service. En présence d’une demande EMAIL approuvée encore en vérification, elle autorise les notifications du compte lié tant que l’adresse Auth confirmée reste l’adresse officielle actuelle. Dès preuve Auth d’une autre adresse et avant finalisation métier, elle diffère l’envoi à l’ancienne boîte. Publication et reprise des notifications utilisent le même contrôle ; une erreur de preuve ne crée aucun faux succès et laisse la notification en échec explicite. La reprise recontrôle le destinataire : un ancien envoi n’est pas réadressé automatiquement après changement d’identité. Les livraisons ordinaires sans demande en cours gardent leur comportement.

Le trigger `employee_invitation_pending_email_guard` interdit en parallèle toute nouvelle invitation PENDING pendant la vérification EMAIL, y compris les voies de publication et renvoi historiques. Il ne bloque pas la révocation de l’ancien lien ni la finalisation. Vérification SQL sous le rôle d’exécution réel : `scripts/tests/payroll-email-delivery-safety.sql`.
